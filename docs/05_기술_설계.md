## 1. 핵심 설계 결정

| # | 결정 | 이유 |
|---|---|---|
| 1 | **타이머 엔진은 포그라운드 서비스 안에서 돈다.** 화면(UI)은 엔진 상태를 받아 보여주기만 한다 | 사용자가 최근 앱 목록에서 앱을 밀어서 닫아도 운동이 계속되어야 한다. 화면 쪽에 엔진을 두면 화면이 닫힐 때 같이 멈춘다 |
| 2 | **시간은 "시작 시각 기준"으로 계산한다** | 1초마다 1씩 빼는 방식은 오래 돌수록 밀린다. 단조 시계(`Stopwatch`)로 경과 시간을 재고, 지금 어느 구간인지를 매번 계산한다 |
| 3 | **엔진 핵심은 순수 Dart로 만든다** (Flutter·플러그인 의존 없음) | 가짜 시계로 단위 테스트를 할 수 있다. 서비스 안이든 화면 쪽이든 그대로 옮겨 쓸 수 있다 |
| 4 | **루틴은 시작 전에 "구간 목록"으로 펼친다** | 마지막 라운드 휴식 건너뛰기, 세트 간 휴식 같은 경계 규칙을 한곳(컴파일러)에서만 처리한다 |
| 5 | **알림(소리·진동·음성)도 미리 계획한다** | 각 구간 안에서 언제 무엇을 알릴지 미리 목록으로 만들어 두고, 엔진은 시간이 된 항목을 실행만 한다 |
| 6 | **서버 없음** | 데이터는 모두 기기 안에 저장한다. 구매 확인은 Google Play를 직접 조회한다 |

## 2. 전체 구조

```
┌──────────────── 화면 (메인 isolate) ────────────────┐
│ 홈 · 편집 · 진행 · 결과 · 설정 · 결제                  │
│        │ 조작 명령            ▲ 상태 스냅샷            │
└────────┼────────────────────┼─────────────────────┘
         ▼                    │      flutter_foreground_task
┌──────────────── 포그라운드 서비스 (별도 isolate) ───────┐   데이터 채널
│  RunController                                       │
│   ├ TimerCore (순수 Dart)  ← 단조 시계                  │
│   ├ CueRunner → BeepPlayer / TtsSpeaker / Vibrator    │
│   ├ 알림 영역 갱신 (남은 시간, 버튼)                     │
│   └ 진행 스냅샷 저장 (이어하기용), 무료 운동 횟수 차감     │
└─────────────────────────────────────────────────────┘
```

### 2.1 화면 ↔ 서비스 통신

| 방향 | 내용 | 시점 |
|---|---|---|
| 화면 → 서비스 | `start(routine)`, `pause`, `resume`, `next`, `prev`, `addRest(10s)`, `stop` | 사용자가 누를 때 |
| 알림 버튼 → 서비스 | `pause` / `resume`, `next` | 알림 영역 버튼을 누를 때 |
| 서비스 → 화면 | `RunSnapshot` (5.3절) | 구간·회차·상태가 바뀔 때, 그리고 1초마다 |

- 화면은 스냅샷에 담긴 "현재 구간이 시작된 시각"을 기준으로 남은 시간과 템포 바를 **화면 쪽에서 매 프레임 보간**해서 그린다. 서비스가 1초에 60번씩 보낼 필요가 없다.
- 화면이 닫혔다가 다시 열리면 서비스에 최신 스냅샷을 요청해서 이어서 그린다.

## 3. 타이머 엔진

### 3.1 구성

| 구성 요소 | 하는 일 | 입력 → 출력 |
|---|---|---|
| `RoutineCompiler` | 루틴을 구간 목록으로 펼친다 | `Routine` → `List<Segment>` |
| `CuePlanner` | 각 구간의 알림 계획을 만든다 (02 문서 6장 표 그대로) | `Segment`, 설정 → `List<Cue>` |
| `TempoClock` | 횟수 모드에서 경과 시간을 회차와 동작 단계로 바꾼다 | 경과 ms, 템포 → (회차, 내려가기/멈춤/올라오기, 단계 진행률) |
| `TimerCore` | 현재 시각에 맞춰 상태를 앞으로 진행하고, 그 사이에 생긴 이벤트를 돌려준다 | `advance(nowMs)` → `List<EngineEvent>` |

### 3.2 동작 방식

```
start:  segments = compile(routine);  stopwatch.start()
tick (서비스 안에서 50ms마다):
   events = core.advance(stopwatch.elapsedMs)
   for e in events:  cueRunner.run(e) / 스냅샷 전송 / 저장
pause:  stopwatch.stop()          resume: stopwatch.start()
```

- `advance`는 "지난번 이후 지나간 시간 동안 일어났어야 할 일"을 모두 돌려준다. 그래서 기기가 잠깐 멈췄다가 깨어나도 건너뛴 구간과 차감 이벤트를 놓치지 않는다. 다만 이미 지나간 알림은 소리를 내지 않고 버린다.
- 일시정지 중에는 `Stopwatch`가 멈추므로 경과 시간에 들어가지 않는다 (02 문서 10.2절 무료 운동 차감 기준과 같음).
- `next`, `prev`, `addRest`는 구간 목록과 오프셋을 직접 고치는 명령이다. 진행 중 조작 규칙은 02 문서 5장을 따른다.

### 3.3 이벤트 종류

| 이벤트 | 사용처 |
|---|---|
| `SegmentStarted(segment)` | 비프·음성, 스냅샷 전송, 진행 상태 저장 |
| `CueDue(cue)` | 카운트다운, "10초 남았습니다", "절반 지났습니다" |
| `TempoPhaseChanged(phase)` | 횟수 모드의 내려가기/멈춤/올라오기 비프 |
| `RepCompleted(n)` | 회차 숫자 음성 |
| `TrialCountable` | 실제 진행 시간이 60초가 된 순간 1번 → 무료 운동 1회 차감 |
| `Finished` | 완료음, 결과 데이터 생성 |

## 4. 소리, 음성, 진동

### 4.1 비프음
- 짧은 소리 파일(낮은 비프, 높은 비프, 짧은 틱, 긴 비프, 완료음)을 앱에 넣고, 운동 시작 전에 **미리 메모리에 올려둔다**.
- `audioplayers`의 `AudioPool` + 저지연 모드(Android SoundPool 기반)를 쓴다. PoC에서 발사 오차 최대 19ms로 확인했다 (10.1절).
- 소리 파일은 `AssetSource`가 아니라 `DeviceFileSource`로 불러온다. 서비스 isolate에서 `path_provider`를 쓰지 않기 위해서다 (10.2절).
- 템포 비프는 박자가 생명이다. 목표는 **예정 시각 대비 50ms 이내**에 소리가 나는 것이다.

### 4.2 음성 (TTS)
- `flutter_tts`로 기기 TTS를 쓴다 (02 문서 6.4절).
- 운동을 시작할 때 앱 언어에 맞는 TTS 언어(`ko-KR`, `en-US`)로 설정하고 빈 문장을 한 번 읽혀서 엔진을 미리 깨워 둔다. 첫 안내가 늦게 나오는 것을 막기 위해서다.
- 새 안내가 오면 `stop()`으로 이전 안내를 끊고 바로 읽는다.
- TTS 시작 지연은 PoC에서 평균 14ms였다. 미리 읽기 보정은 하지 않는다. 다른 기기에서 지연이 크면 다시 검토한다.

### 4.2-1 다국어 (2026-11-20 추가)

- 화면 문구: `flutter gen-l10n` + ARB (`lib/l10n/app_ko.arb`가 기준, `app_en.arb`). 화면에서는 `context.l10n.키`로 쓴다.
- 서비스 isolate에는 BuildContext가 없으므로 `l10nFor(locale)`로 문구를 찾는다. 언어는 저장된 설정(`AppSettings.language`), 없으면 기기 언어.
- 음성 안내 문구는 ARB가 아니라 엔진의 `CueText`(언어별 Dart 클래스)에 둔다. 한국어 고유어 수사, 영어 복수형처럼 문법 처리가 필요하고, 엔진 테스트를 Flutter 없이 돌리기 위해서다.
- 언어 고르기: `resolveLocale` — 지원하는 언어 중 맞는 것, 없으면 영어.
- Android 13+ 앱별 언어: `res/xml/locales_config.xml`로 지원 언어를 알리고, `fitness_timer/system` 채널(`getAppLocale`, `setAppLocale`)로 앱 설정과 맞춘다 (`AppLanguage`). 앱 시작과 앱으로 돌아올 때 시스템 값을 가져온다.
- 언어를 추가할 때: ARB 파일, `CueText` 구현, `AppSettings.languageChoices`, 설정 화면 목록, `locales_config.xml`, iOS `CFBundleLocalizations`.

### 4.3 다른 앱 음악과 함께 쓰기
- **음성 안내가 나오는 동안만** "볼륨 줄이기 허용" 포커스(`gainTransientMayDuck`)를 요청하고, 안내가 끝나면 바로 반납한다. 운동 내내 포커스를 잡으면 음악이 계속 작게 들리기 때문이다. `flutter_tts`의 `speak(text, focus: true)`가 이 동작을 스스로 하므로 별도 패키지가 필요 없다 (10.1절).
- 비프음은 오디오 포커스를 **요청하지 않는다** (`audioFocus: none`). `audioplayers` 기본값은 포커스 독점이라 음악이 멈추므로 반드시 바꿔야 한다 (10.1절).
- 재생 채널은 미디어 볼륨을 쓴다 (02 문서 6.5절).

### 4.4 진동
- 짧게/길게/길게 2번 패턴을 쓴다. `vibration` 패키지 후보.

## 5. 데이터 구조와 저장

### 5.1 저장소

| 데이터 | 저장 방식 | 쓰는 쪽 |
|---|---|---|
| 루틴 목록, 즐겨찾기, 최근 사용, 정렬, 순서, 코스, 홈 "내 운동"에서 마지막으로 본 탭 | `routines.json` | 화면 |
| 설정 | `settings.json` | 화면 (서비스에는 시작할 때 값을 넘김) |
| 진행 스냅샷 (이어하기) | `run_snapshot.json` | 서비스 (저장·삭제), 화면 (읽기) |
| 무료 운동 사용 횟수 | 결제 단계에서 결정 | 서비스 (차감), 화면 (읽기) |

- 모두 앱 문서 폴더의 JSON 파일이다. 임시 파일에 쓴 뒤 이름을 바꿔서, 쓰는 도중 앱이 꺼져도 기존 파일이 깨지지 않게 한다 (`JsonFile`).
- 처음에는 `SharedPreferencesAsync`를 쓰려 했지만, 서비스 isolate에서 플러그인 문제(10.2절)를 피하고 테스트하기 쉽도록 `dart:io` 파일로 바꿨다. 폴더 경로는 화면 쪽에서 구해 서비스에 넘긴다. (2026-11-19 변경)
- 진행 스냅샷의 저장과 삭제는 순서대로 처리한다. 저장이 끝나기 전에 삭제가 먼저 끝나면, 끝난 운동의 파일이 되살아나 이어하기 창이 잘못 뜨기 때문이다.
- 루틴은 많아야 수십 개라서 DB 없이 JSON 파일 하나로 충분하다. 파일에 `schemaVersion`을 넣어 나중에 구조가 바뀌면 변환한다.
- 서비스는 루틴 파일을 읽지 않는다. 시작할 때 화면이 진행할 운동(`Workout`: 루틴 하나 또는 코스의 루틴 전체)을 통째로 넘긴다.
- 코스(`courses`, `courseOrder`)는 루틴과 같은 파일에 넣었다. 루틴을 지울 때 코스에서 빼는 일을 한 번에 저장하기 위해서다. 필드만 추가했으므로 `schemaVersion`은 그대로 1이다. (2026-11-20)

### 5.2 모델

```dart
class Routine {
  String id;              // uuid
  String name;            // 1~20자
  bool isPreset;
  EndCondition endCondition;  // time | reps
  int prepMs;
  int workMs;             // 시간 모드
  int targetReps;         // 횟수 모드
  Tempo tempo;            // 횟수 모드: downMs, holdMs, upMs
  int restMs;
  int rounds;
  int sets;               // 횟수 모드에서는 항상 1
  int setRestMs;
  bool skipLastRest;
  CueStyle cueStyle;      // numbersOnly | actionAndNumbers | beepOnly
  bool favorite;
  DateTime createdAt;
  DateTime? lastUsedAt;
}

class Segment {
  SegmentType type;       // prep | work | rest | setRest | courseRest
  int? durationMs;        // 시간 모드 work, 모든 prep/rest
  int? targetReps;        // 횟수 모드 work
  int round;              // 1부터
  int set;                // 1부터
  int part;               // 코스 안의 루틴 번호 (0부터). 루틴 사이 휴식은 다음 루틴 번호
}

// 코스 (2026-11-20). 루틴은 id로 가리킨다.
class Course { String id; String name; List<CourseStep> steps; }
class CourseStep { String routineId; int restAfterMs; }  // 0 = 휴식 없음

// 엔진이 실제로 진행하는 단위: 루틴 하나 또는 코스
class Workout {
  String name;
  List<Routine> routines;
  List<int> restsMs;      // routines[i] 뒤의 휴식, 길이 = routines.length - 1
  String? courseId;       // 코스이면 값이 있다
}
```

- 엔진(`TimerCore.workout`)은 `RoutineCompiler.compileWorkout`으로 루틴들의 구간을 이어 붙인 목록 하나를 돈다. 첫 루틴만 준비 구간을 넣고, 루틴 사이에 `courseRest` 구간을 넣는다 (0이면 넣지 않음).
- 알림 계획, 템포, 이어하기의 횟수 보정은 구간의 `part`로 그 루틴을 찾아 그 루틴 설정으로 한다.
- 루틴 하나도 `Workout.single`로 같은 길을 탄다. 그래서 서비스·이어하기·화면 코드는 루틴과 코스를 구분하지 않는다.

- 시간은 모두 **밀리초 정수**로 저장한다. 템포의 0.5초 단위를 오차 없이 표현하기 위해서다.
- 프리셋은 코드에 상수로 두고 파일에는 저장하지 않는다.

### 5.3 진행 스냅샷

```dart
class RunSnapshot {
  Workout workout;        // 이어하기 때 다시 컴파일하기 위해 통째로 저장 (코스면 루틴 전체)
                          // 코스 기능 전 파일의 routine 키도 읽는다
  int segmentIndex;
  int segmentElapsedMs;
  int totalElapsedMs;     // 일시정지 제외
  RunStatus status;       // running | paused | finished
  int? currentRep;        // 횟수 모드
  TempoPhase? tempoPhase;
  int segmentStartedAtEpochMs;  // 화면 보간용
  bool trialCounted;
  DateTime savedAt;       // 30분 지나면 이어하기 대상에서 제외
}
```
- 구간이 바뀔 때, 조작할 때(일시정지·다음 등), 그리고 진행 5초마다 저장한다. 정상적으로 끝나거나 중단하면 지운다.
- 이어하기는 저장된 위치에서 **일시정지 상태로** 엔진을 복원한다 (`TimerCore.restore`).
- 시스템이 서비스를 되살린 경우(`TaskStarter.system`)에는 운동을 처음부터 몰래 다시 시작하지 않고 서비스를 내린다. 저장된 상태는 남겨 두고, 사용자가 앱을 열면 이어하기 창으로 묻는다.

## 6. Android 백그라운드 동작

### 6.1 포그라운드 서비스
- `flutter_foreground_task`로 서비스를 띄우고, 그 안의 `TaskHandler`에서 `RunController`를 돌린다.
- 이 서비스는 별도 Flutter 엔진에서 돌기 때문에 TTS·오디오 플러그인이 그 안에서도 정상 동작하는지 **PoC에서 반드시 확인**한다. 동작하지 않으면 "엔진은 서비스, 소리는 화면 쪽" 구조로 바꾸는 대안을 검토한다.
- **화면이 꺼져도 CPU가 잠들지 않도록** 서비스 실행 중 wake lock을 잡는다. 운동이 끝나거나 중단되면 즉시 놓는다.

### 6.2 권한과 서비스 유형

| 항목 | 내용 |
|---|---|
| `POST_NOTIFICATIONS` | Android 13 이상, 첫 ▶ 때 요청 (03 문서 D2) |
| `FOREGROUND_SERVICE` + 서비스 유형 | Android 14 이상은 유형을 지정해야 한다. 운동 타이머는 정해진 유형에 딱 맞지 않아 **`specialUse` + Play Console 사용 사유 신고**가 유력하다. 출시 전에 Google Play 정책을 확인해서 확정한다 |
| `WAKE_LOCK` | 6.1절 |
| `VIBRATE` | 진동 |
| 배터리 최적화 | `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` 권한은 Play 정책상 제한이 있어 쓰지 않는다. 대신 설정 화면으로 이동하는 안내만 한다 (6.3절) |

### 6.3 제조사 배터리 최적화 대응
삼성·샤오미 등은 백그라운드 앱을 강하게 종료한다. 운동 타이머 앱에서 가장 흔한 불만 원인이다.
- 1차 방어: 포그라운드 서비스와 wake lock
- 2차 방어: 진행 스냅샷 저장 → 앱을 다시 열면 이어하기 (03 문서 D1)
- 3차 방어: 운동이 비정상 종료된 흔적이 발견되면, 다음 실행 때 **배터리 최적화 해제 방법 안내**를 띄운다. 제조사별로 설정 위치가 다르므로 기기 제조사를 확인해 맞는 안내를 보여준다.

### 6.4 화면 꺼짐 방지
- 진행 화면이 열려 있을 때만 `wakelock_plus`로 화면을 켜 둔다 (설정에서 끌 수 있음).

## 7. 결제와 무료 체험

- `in_app_purchase`로 비소모성 상품 `fitness_timer`를 판다.
- 앱을 시작할 때 `purchaseStream`을 구독하고, 구매 내역을 조회해서 정식 버전 여부를 판단한다. 결과는 기기에 저장해서 오프라인일 때 쓴다 (02 문서 10.5절).
- 구매가 들어오면 `completePurchase`로 확정한다. 확정하지 않으면 Google Play가 3일 뒤 자동 환불한다.
- 무료 운동 차감은 서비스가 `TrialCountable` 이벤트를 받을 때 한다. 화면은 홈 배지와 잠금 여부를 판단할 때 그 값을 읽는다.
- 잠금 판단은 한 곳(`Entitlement`)에서만 한다: `isFull || freeWorkoutsUsed < 15`이면 내 루틴 기능을 쓸 수 있다. 프리셋은 항상 실행할 수 있다.
- 무료 운동 사용 횟수는 `trial.json`에 저장한다. 서비스가 `TrialCountable` 이벤트에서 1 늘리고, 화면은 홈·결과 화면에서 다시 읽는다. 동시에 여러 번 차감돼도 빠지지 않게 순서대로 처리한다.
- 구매 상태는 `purchase.json`에 캐시한다. 앱을 시작할 때 Android `queryPastPurchases`로 구매 내역을 조회해 맞춘다. 조회에 실패하면(오프라인) 캐시 값을 쓴다. 확정(acknowledge)되지 않은 구매는 이때도 확정한다.
- 디버그 빌드에서만 설정 화면에 개발용 메뉴를 보여준다: "결제 없이 정식 버전으로 보기", 무료 사용 횟수 바꾸기. Play Console 상품이 없어도 잠금·해제 흐름을 확인하기 위해서다.
- 실제 결제 테스트는 Play Console 준비(본인 확인, 결제 프로필, 앱 생성, 내부 테스트 트랙 업로드, 상품 `fitness_timer` 생성, 라이선스 테스터 등록) 뒤에 한다.

- 상태 관리는 MVP에서는 Flutter 기본 `ChangeNotifier` + `ListenableBuilder`로 한다 (`RoutineStore`, `RunClient`). 화면과 상태가 적어 별도 패키지가 필요 없다. 상태가 늘어나 관리가 어려워지면 `flutter_riverpod` 도입을 다시 검토한다. (2026-11-19 변경)
- `engine/`은 Flutter를 import하지 않는다. 이 규칙은 린트 또는 테스트로 강제한다.

### 10.1 PoC 결과 (2026-11-18)

- 기기: 삼성 갤럭시 Z 폴드7 (SM-F966N), Android 17 (API 37), One UI 9
- 코드: `poc/bg_audio_poc/` (flutter_foreground_task 11.0.3, flutter_tts 4.2.5, audioplayers 6.8.1)
- 테스트 루틴: 67초 사이클 반복 (준비 → 횟수 모드 8회 템포 2-0-1 → 휴식 15초 → 운동 20초)

| # | 항목 | 결과 | 판정 |
|---|---|---|---|
| 1 | 서비스 isolate 안에서 TTS·비프 재생 | 정상. 박자와 한국어 음성 모두 자연스러움 (사용자 확인) | ✅ |
| 2 | 화면 끈 상태 31분 시간 오차 | 최대 2ms. 타이머 끊김 0회, 건너뛴 알림 0개 (알림 1,119개) | ✅ |
| 2-1 | 강제 깊은 절전 모드(`deviceidle force-idle` + 충전 해제 흉내) 2분 30초 | 알림 83개 정상, 끊김 0회, 오차 0ms | ✅ |
| 3 | 비프 발사 시각 오차 (코드가 재생을 요청한 시각 기준) | 대부분 2~3ms, 최대 19ms | ✅ |
| 4 | TTS 시작 지연 | 평균 14ms, p95 20ms, 최대 207ms (1번) → **미리 읽기 보정 불필요** | ✅ |
| 5 | 음성 안내 중 음악 볼륨 줄이기 | 처음엔 **음악이 멈춤** → 수정 후 정상 (아래 참고) | ✅ |
| 6 | 최근 앱 목록에서 밀어서 닫기 | 서비스가 계속 동작, 소리 유지 | ✅ |
| 7 | 저사양 기기 글래스 화면 성능 | 미확인 (저사양 기기 필요) | ⏳ |

**발견한 문제와 해결**
- **음악이 멈춘 원인**: `audioplayers`의 기본 오디오 설정이 `AUDIOFOCUS_GAIN`(오디오 독점)이었다. 비프음이 날 때마다 다른 앱 음악이 정지됐다.
  - 해결: 비프 재생기의 `AudioContextAndroid`를 `audioFocus: none`, `contentType: sonification`, `usageType: media`로 설정한다. 비프는 음악 위에 겹쳐서 나고, 음악 볼륨 줄이기는 TTS(`speak(text, focus: true)`)가 맡는다.
  - `flutter_tts`는 `focus: true`일 때 스스로 `AUDIOFOCUS_GAIN_TRANSIENT_MAY_DUCK`을 요청하고 말이 끝나면 반납한다. 그래서 4.3절에서 계획한 `audio_session` 패키지는 **필요 없다.**
- **서비스 시작 시 오류**: 서비스 isolate에서 플러그인 객체(`FlutterTts`)를 필드 초기화로 만들면 바인딩 초기화 전이라 실패한다. 서비스 진입점에서 `WidgetsFlutterBinding.ensureInitialized()`를 부르고, 플러그인 객체는 `onStart` 안에서 만든다.
- **서비스 유형**: `specialUse` + `PROPERTY_SPECIAL_USE_FGS_SUBTYPE` 선언으로 Android 17에서 정상 시작됐다. Play Console 신고 가능 여부는 여전히 확인 필요.
- **TTS 패키지 조회 선언**: Android 11 이상에서는 매니페스트 `<queries>`에 `android.intent.action.TTS_SERVICE`를 넣어야 한다.

**한계와 남은 확인**
- 31분 테스트는 USB로 **충전 중**이었다. 충전 중에는 절전 모드가 걸리지 않으므로, 강제 절전 테스트(2-1)로 보완했다.
- **삼성 자체 배터리 관리**(앱 절전, 사용하지 않는 앱 재우기)는 명령으로 재현할 수 없다. USB를 뽑고 실제 운동처럼 30분 이상 쓰는 테스트가 개발 중에 필요하다.
- 앱을 밀어서 닫은 뒤 알림을 눌러 다시 열 때, 화면이 뜨는 순간 비프 1개가 88ms 늦고 TTS 1개가 349ms 늦었다. 순간적인 부하로 보이며, 본 개발에서 재현되면 원인을 확인한다.
- 샤오미·픽셀, 저사양 기기는 아직 확인하지 않았다.

**결론: 1장 결정 1번(엔진을 포그라운드 서비스 안에서 돌린다) 구조를 그대로 확정한다.**

### 10.2 본 앱 연결 중 발견한 문제 (2026-11-19)

| 문제 | 원인 | 해결 |
|---|---|---|
| 시작하면 무한 로딩, 비프음 없음 | `path_provider_android` 2.3.x가 쓰는 `jni` 1.2.0이 이 기기에서 `ClassNotFoundException: android/content/Context`로 실패 (화면·서비스 isolate 모두). `audioplayers`의 `AssetSource`가 내부에서 `path_provider`를 씀 | ① `pubspec.yaml`의 `dependency_overrides`로 `path_provider_android`를 jni를 쓰지 않는 2.2.x로 고정 ② 비프음 파일은 화면 isolate에서 앱 저장소로 복사(`SoundFiles.prepare`)하고, 서비스는 경로만 받아 `DeviceFileSource`로 재생 |
| 운동을 끝내고 4초 안에 다른 운동을 시작하면 무한 로딩 | 끝난 서비스가 완료음 재생 후 내려가도록 걸어 둔 4초 예약이 새로 시작한 서비스까지 내림 | 예약을 `Timer`로 바꿔 `onDestroy`에서 취소. 화면은 이전 서비스가 완전히 내려간 뒤 시작. 6초 안에 상태가 오지 않으면 무한 로딩 대신 실패 안내 |
| 가로 화면에서 노란·검은 줄무늬 | 진행 화면이 세로 기준이라 높이가 넘침 | 03 문서 5.3절 가로 배치 구현, 정보 영역은 공간이 부족하면 비율대로 축소 |

- `jni` 1.1.2로 내리는 방법은 `jni_flutter`와 맞지 않아 빌드가 실패했다.
- `path_provider_android` 고정은 임시 조치다. 버전을 올릴 때는 반드시 실기기에서 확인한다.
